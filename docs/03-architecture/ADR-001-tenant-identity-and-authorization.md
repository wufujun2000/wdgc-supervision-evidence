# ADR-001：统一账号、租户成员与项目成员的身份权限体系

## 1. 背景

FastapiAdmin 原生基线只提供平台式 `sys_user / sys_role / sys_user_roles` 用户权限体系。当前 B0 实现采用 `sys_user + biz_tenant_user` 绑定，并以 `is_enterprise_admin` 表示企业管理员，已经能够支持租户开通和行级隔离，但不能表达以下业务事实：

1. 租户需要唯一的企业拥有者，以及可有多名、权限可分配的企业管理员；
2. 企业管理员即使获得全部可委托权限，也不能替代企业拥有者；
3. 总监、专监、监理员是项目级任命，不是租户级角色；同一成员可在不同项目承担不同项目角色；
4. 平台和企业拥有者均需要可审计的所有权移交能力；
5. 产品团队正在重写 PRD，账号、身份、权限和项目任命必须先由技术架构统一，不能让产品或各开发任务分别推断。

## 2. 决策

采用 **“统一账号、租户成员、项目成员”三层模型**：

- **统一账号**：解决“谁能登录”，复用一套认证、密码、微信、会话和账号状态能力；
- **租户成员**：解决“属于哪家企业、拥有哪些租户管理权限”；
- **项目成员**：解决“在哪个项目担任何职、负责哪些危大类别”。

**平台定义角色模板和权限目录，租户负责租户授权和项目任命。**

不另建一套带密码、微信登录和会话管理的租户认证用户表，也严禁把租户角色或项目角色写入平台原生 `sys_user_roles`。

## 3. 三层身份模型

### 3.1 统一登录账号：`sys_user`

`sys_user` 是认证身份，不直接代表平台权限、租户权限或项目权限。

- 登录认证、密码哈希、微信身份、账号状态、会话管理继续复用 FastapiAdmin 能力；
- `sys_role / sys_user_roles` 只承载平台域角色与权限；
- 一个账号是否具有租户身份，必须经 `biz_tenant_member` 解析；
- 一个账号是否具有项目身份，必须经当前租户下的 `biz_project_member` 解析；
- `sys_user.is_superuser` 仅表示平台超级管理员，不表示任何租户的企业拥有者。

本决策明确替代总体架构 v1.5 第 3.1 节“`sys_user` 100% 仅供平台人员使用”的旧口径：**账号表可以统一，授权表必须分域。**

### 3.2 租户成员：`biz_tenant_member`

租户成员是账号在某个企业中的成员身份，建议最小字段为：

- `id`：租户成员主键，后续租户业务归属优先引用该 ID；
- `tenant_id`：所属租户；
- `user_id`：关联 `sys_user.id`；
- `emp_no`：企业内工号；
- `status`：成员状态；
- 创建、更新、停用等审计字段。

约束：

- `(tenant_id, user_id)` 唯一；不再用 `user_id` 单列唯一把“一人一租户”固化为数据库限制；
- 是否允许一个自然人同时加入多个租户由业务规则控制，不影响成员模型；
- 成员停用后禁止继续访问租户，但不得物理删除已被任务、采集、审核、签署或审计记录引用的成员；
- 当前 `biz_tenant_user` 是过渡实现，实施时迁移为 `biz_tenant_member`，已有数据保留。

### 3.3 项目成员：`biz_project_member`

项目角色只能按项目任命：

- `biz_project`：项目主体；
- `biz_project_member`：`tenant_id + project_id + member_id + role_code + status`；
- `biz_project_member_hazard`：专监在指定项目内负责的危大类别集合。

规则：

- 项目角色为 `SZ`（总监）、`SP`（专监）、`SA`（监理员）；
- 同一成员可在项目 A 任 `SP`、在项目 B 任 `SZ`；
- `SZ` 的项目范围为当前项目全部危大类别；`SP` 必须绑定危大类别；`SA` 以项目内本人任务和本人采集记录为主要范围；
- 租户角色不会自动派生项目角色，企业拥有者或企业管理员如需履行项目法定职责，仍须单独获得项目任命；
- 项目任命变化不得改写历史证据中的当时角色、签署人和采集人归属。

## 4. 角色与命名

| 作用域 | 系统标识 | 产品显示名 | 数量与授予方式 |
| :--- | :--- | :--- | :--- |
| 平台 | `SUPERADMIN` | 平台超级管理员 | 平台侧授权；默认具有所有权移交的兜底权限 |
| 平台 | `SYSADMIN` | 平台系统管理员 | 平台侧授权；负责租户开通等日常工作 |
| 租户 | `TENANT_OWNER` | **企业拥有者** | 每租户恰好一名；只能通过开通初始化和专门的所有权移交变更 |
| 租户 | `TENANT_ADMIN` | **企业管理员** | 零至多名；由企业拥有者或具有相应管理权限者设置，权限单独授予 |
| 项目 | `SZ` | 总监 | 按项目任命 |
| 项目 | `SP` | 专业监理工程师（专监） | 按项目任命并绑定危大类别 |
| 项目 | `SA` | 监理员 | 按项目任命 |

术语约束：

- “企业拥有者”是系统内租户所有权标识，不代表股权、法定代表人身份；
- “企业管理员”不得简称为“系统管理员”，避免与平台 `SYSADMIN` 混淆；
- “租户超管”只能作为企业拥有者的解释性别名，不另设角色，也不作为 PRD 的正式角色名；
- 产品界面使用“租户成员”或“企业成员”，不使用容易与付费会员混淆的“会员”。

## 5. 企业拥有者：唯一身份与权限边界

### 5.1 单持有人模型

- 每个租户在任意时刻**恰好一名有效 `TENANT_OWNER`**；
- `TENANT_OWNER` 不是可普通分配的多人角色，不出现在普通角色授权列表中；
- 平台开通租户时，首名租户成员自动成为初始企业拥有者；
- 企业拥有者默认拥有全部租户管理权限，但不自动拥有平台权限或项目法定签署权。

推荐使用单独的单持有人记录，例如 `biz_tenant_owner`：

- `tenant_id` 主键或唯一约束，保证一个租户只有一条有效所有权记录；
- `member_id` 指向当前企业拥有者；
- `version` 或等效字段用于并发控制；
- 企业拥有者身份由该记录派生，不在 `biz_tenant_member_role` 中保存可产生多条 Owner 的普通角色记录。

### 5.2 企业管理员不是企业拥有者

企业拥有者是“**所有权身份 + 全部租户权限**”；企业管理员是“**可委托权限集合**”。

- 企业管理员可以获得零到全部可委托权限，日常功能可能看起来与企业拥有者相同；
- 即使获得全部可委托权限，也不能移交所有权、创建 Owner、修改 Owner 身份或执行 `owner_only` 动作；
- 企业管理员不能通过普通成员管理停用、删除或降权企业拥有者；
- 企业管理员不能被授予超出其自身可转授范围的权限；
- 平台 `SUPERADMIN` 执行所有权移交只是平台管理动作，不因此成为企业拥有者，也不获得该租户日常业务权限。

### 5.3 两类服务端校验

- 普通管理功能使用 `require_permission(...)`：企业拥有者默认通过，企业管理员按授权判断；
- 所有权专属功能使用 `require_owner()`：只认可当前有效所有权记录，不以权限数量、菜单可见性或 `TENANT_ADMIN` 身份代替。

平台权限目录应为权限标识其可委托属性：

- `delegable=true`：可按规则授予企业管理员；
- `owner_only=true`：不可委托，目前至少包括所有权移交。

前端隐藏按钮只用于体验，不能替代上述服务端校验。

## 6. 所有权移交

### 6.1 发起路径

| 发起方 | 权限与条件 |
| :--- | :--- |
| 平台 | 仅具有专门 `tenant_owner_transfer` 权限的平台账号；默认仅 `SUPERADMIN`。必须填写原因并二次确认，用于 Owner 离职、停用、失联等处置 |
| 租户内 | 仅当前企业拥有者；目标为本租户其他有效成员；必须二次确认 |

共同约束：

- 目标必须是同一租户的有效成员，不能是其他租户成员、平台账号或已停用成员；
- 租户冻结期间禁止租户侧发起，平台侧保留处置能力；
- 一期采用确认后直接生效，不引入“待接收人接受”的异步流程。

### 6.2 原子性与结果

移交必须在同一数据库事务内完成，并通过租户/所有权记录行锁、版本校验或等效机制防止并发双 Owner：

1. 校验发起方、当前 Owner 和目标成员；
2. 将所有权记录切换到目标成员；
3. 原 Owner 同时失去企业拥有者身份；
4. 写入审计记录；
5. 刷新或清退双方租户会话，使新权限立即生效。

任何时刻不得出现“零 Owner”或“双 Owner”的已提交状态。

移交只改变租户所有权：

- 双方登录账号不变；
- 历史采集、审核、签署和审计归属不变；
- 双方项目任命不变；
- 原 Owner 保留租户成员身份，但不自动保留企业管理员权限；如仍需 `TENANT_ADMIN`，由新 Owner 另行授权。

审计至少记录：发起来源（平台/租户）、操作人、租户、原 Owner、新 Owner、时间、原因和结果。

## 7. 平台角色模板与租户授权

### 7.1 平台职责

平台维护全局角色模板、权限目录和权限作用域：

- 租户角色模板：`TENANT_OWNER`、`TENANT_ADMIN`；
- 项目角色模板：`SZ`、`SP`、`SA`；
- 权限目录至少区分：租户成员管理、企业管理员及权限管理、项目管理、项目成员任命，以及后续业务权限；
- 角色模板和权限目录的变更走平台受控变更与审计，不允许租户自行发明系统级角色。

### 7.2 租户职责

企业拥有者及获得相应权限的企业管理员执行：

- 新增、停用租户成员；
- 设置企业管理员并分配其可委托权限；
- 创建项目；
- 在项目中任命 `SZ/SP/SA`，并为 `SP` 绑定危大类别。

建议将以下能力分开授权，不以一个“管理”权限笼统覆盖：

- `tenant_member_manage`；
- `tenant_admin_manage`；
- `project_manage`；
- `project_member_assign`。

只有拥有相应权限才可执行对应动作；任何授权都不得超过操作者自身的可转授范围，也不得包含 `owner_only` 权限。

## 8. 会话、隔离与安全约束

1. 登录后先得到账号身份；访问租户接口时，由服务端根据账号、目标租户和有效成员记录解析 `tenant_id + member_id`，禁止信任客户端自行声明的租户身份。
2. 项目上下文必须由服务端根据当前成员的项目任命校验；`X-Project-Id` 等请求头只能表达选择，不能作为授权依据。
3. 平台账号没有有效租户成员记录时不能访问租户接口；租户成员没有平台角色时不能访问平台接口。
4. 所有租户成员、授权、项目、项目任命及专监危大范围表均包含 `tenant_id`，并纳入既有行级隔离和跨租户测试。
5. 冻结租户、停用账号或停用成员必须使既有会话失效；保留历史业务与审计记录，不做物理删除。
6. 平台受控代管继续执行既有“默认只读、二次授权、完整审计、不得代签”规则，与企业拥有者身份无关。

## 9. 关键业务流程

### 9.1 平台开通租户

同一事务中完成：

1. 创建企业租户；
2. 创建或绑定首名登录账号；
3. 创建首名租户成员；
4. 创建唯一企业拥有者记录；
5. 写入开通审计。

任一步失败整体回滚，不留下没有 Owner 的可用租户。

### 9.2 租户新增成员与管理员

1. 有 `tenant_member_manage` 权限的成员创建或绑定账号并形成租户成员；
2. 企业拥有者或具有 `tenant_admin_manage` 权限的成员设置企业管理员；
3. 在可委托、可转授范围内分配权限；
4. 未获项目任命的成员不具有任何项目角色。

### 9.3 项目创建与任命

1. 有 `project_manage` 权限的成员创建项目；
2. 有 `project_member_assign` 权限的成员从本租户有效成员中任命项目角色；
3. 为专监绑定本项目危大类别；
4. 项目接口按当前项目角色和危大范围授权。

## 10. 对现有文档与实现的影响

本 ADR 生效后，以下旧口径在本决策范围内以本 ADR 为准：

- 总体架构 v1.5 第 3.1 节：`sys_user` 仅供平台人员使用、`biz_tenant_user` 作为员工表的表述；
- 总体架构 v1.5 第 4.2 节：仅以 `is_enterprise_admin` 判断企业管理员的表述；
- PRD v2.4 第 3 章：以单一 `ADMIN` 表示企业管理员的表述；
- 当前 B0 代码：`biz_tenant_user + is_enterprise_admin + user_id UNIQUE` 的过渡模型。

现有 B0 的租户开通、行级隔离、冻结清退会话、测试和平台页面不需要推倒重做；实施时按本 ADR 迁移账号绑定与授权部分，并同步总体架构文档。

本 ADR 不决定：

- 新源文 V/P、215 节点、字段集、命名、留存等新契约 D-1~D-6；
- 节点库方案甲的具体数据表；
- 采集、审核、证据、出证业务状态机；
- FastapiAdmin 选型 ADR。

上述事项分别按既有决策流程处理，不因本 ADR 提前开发。

## 11. 开发验收条件

1. 每租户始终恰好一名有效企业拥有者，并发移交测试不能产生零 Owner 或双 Owner；
2. 企业管理员即使获得全部可委托权限，调用所有权专属接口仍被拒绝；
3. 企业管理员不能停用、删除、降权 Owner，不能跨租户移交或授权；
4. 平台有权限账号可移交所有权但不成为租户 Owner，平台无权限账号被拒绝；
5. 原 Owner 移交后权限立即失效，新 Owner 权限立即可用，双方项目任命及历史归属不变；
6. `SZ/SP/SA` 只能按项目生效，同一成员在不同项目可具有不同角色，专监危大范围隔离有效；
7. 未获项目任命的企业拥有者/企业管理员不能代行项目法定签署；
8. 跨租户成员、授权、项目与任命数据隔离测试通过；
9. 既有 B0 隔离、开通和冻结测试继续通过，并补充本 ADR 的权限与移交测试。

## 12. 结论

本决策将登录认证、租户所有权、租户管理授权和项目法定任命拆开，既复用 FastapiAdmin 的认证底座，又避免平台 RBAC 与租户、项目权限混杂。后续开发以本 ADR 为身份权限唯一基线。技术团队提供配套素材、实现事实与验收证据，由第三方评审结合既有推进路线整合形成正式产品交接和统一口径，产品团队依据评审发布的文件编写 PRD 和原型，不再另行推断底层账号体系。
