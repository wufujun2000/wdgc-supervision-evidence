## 四、仍未闭环的 P0 问题

### P0-01：架构仍残留一处错误表号

**位置：**`docs/system-architecture-design.md` 第 256 行。

当前仍写：

> 工程暂停令，GB/T 50319 表 A.0.4

应改为 **A.0.5**。现有 CI 只扫描 PRD 的旧表号组合和字典内容，没有扫描架构中的该错误，因此 53/53 未能发现。

### P0-02：PRD 与架构仍不是唯一契约

1. **扩展列数量错误仍在 PRD 首页**

   `PRD_v2.3_评审整改中.md` 第 18 行仍写“25 个内部扩展列”，实际字典和 README 均为 28 个。生成脚本第 93 行仍硬编码 25，现有 CI 未检查 PRD 首页数量。

2. **架构旧命名公式仍在**

   架构第 160、163 行仍使用 `node_code` 公式，没有包含 PRD 已确定的 `subcategory_code + node_uid_suffix`。

   当前 CI 只检查架构中是否出现 `legacy_node_code` 和 `file_sha256`，因此即使旧公式继续存在也会通过。

3. **任务字段仍有旧名称**

   架构第 156 行仍使用 `task_instance_id`，字典和 PRD 为 `task_occurrence_id`。

   当前“无旧模型”断言只排除完整字符串 `biz_task_instance`，无法发现 `task_instance_id`。

4. **超管代管审批描述仍在**

   架构第 116 行仍写“可单独二次授权审批/导出”，第 118 行仍以“审核影像”为代管调用示例，与 PRD 的默认只读及不得代替法定责任人审批不一致。

   当前 CI 只检查“不得代替法定责任人签字”这句话是否存在，没有排除同文档其他段落继续授予审批能力。

### P0-03：示例虽然可解析，但不再满足字段类型契约

示例一当前值为：

- `raw_frame_sha256=demo_raw_frame_sha256_placeholder_not_real`，长度 42；
- `file_sha256=demo_archive_file_sha256_placeholder_not_real`，长度 45。

二者都不是 64 位十六进制 SHA-256，不符合对应 `CHAR(64)` 契约。建议：

- 使用明确为演示用途的 64 位十六进制值；
- 另增 `example_data_status=SYNTHETIC` 或在示例标题中声明“合成演示数据”；
- 不要让示例为了表达“演示”而破坏自身 Schema。

同时，`position_desc` 被改为“钢结构吊装、索膜张拉专项方案编审与专家论证”，这是节点名称，不是 B103 所定义的现场部位。无实际部位时应为 `null`，或填写真实楼栋/楼层/分区，不能用节点名称替代位置。

### P0-04：部分 CI 断言存在“新词存在即通过”的盲区

当前典型问题：

- 检查新字段名存在，但不检查旧公式是否同时存在；
- 检查禁止超管代签的声明存在，但不检查其他段落是否仍授予审批；
- 检查 `biz_task_instance` 不存在，但未覆盖 `task_instance_id`；
- 对待审示例也执行“哈希演示值”检查，但该示例没有哈希字段；断言实际只是检查整个 PRD 是否包含另一示例的两个演示字符串；
- 成功项 `detail` 仍显示“存在重复 node_uid”“缺少 TC-REV-05”等失败文案，容易误导审阅者；
- README 仍写 37 项校验，没有同步为 53 项。

建议将断言改为“正向契约 + 反向排除 + 逐示例结构校验”，并纳入 README 与架构全部相关章节。
