> 报告编号：WDGC-PRD-V21-FOLLOWUP-20261114  
> 复审日期：2026-11-14  
> 呈送对象：产品负责人、项目负责人、技术负责人及相关评审人员

> 评审性质：整改有效性复核与开发准入审查

## 一、复审结论

**本轮整改方向通过，但开发基线不通过。**

产品负责人及其团队已对前次审查意见作出实质性回应，部分关键问题得到有效修正，包括节点及字段数量复算、双哈希分离、离线字节配额、认证状态枚举、表单标准表号和受控代管验收规则等。

但本次复审发现，当前版本仍存在以下根本问题：

1. 文首核销表和架构说明中的修正，没有完整同步到 PRD 正文、ER 模型、页面规则及验收用例；
2. 节点种子库存在大量重复节点编码，与数据库唯一键设计直接冲突；
3. 原始材料中的空白风险等级被擅自补值，部分原始内容错误未经业务校审即进入种子库；
4. 字段名称、类型、长度和生成主体仍存在跨文件冲突；
5. 严重隐患停工报告、文书送达签认和验收后工序放行尚未形成完整业务闭环；
6. 容量、性能、隐私合规及部分移动端能力仍未形成可验证的一致口径。

因此，**不能将当前版本认定为“12 项问题全部核销、可直接指导全量开发的正式闭环版”。**建议允许继续修订文档并开展有限范围的技术 PoC，但不建议将 PRD v2.1 和现有 JSON 基线直接作为全量开发的唯一契约。

## 三、确认有效的整改成果

### 3.1 机器可读基线已建立

两份 JSON 均通过语法解析，已形成从文档描述向机器可读契约转化的基本结构：

- 节点种子库共有 **347 条记录**，各分类条数与汇总一致；
- 元数据字典共有 **24 个标准字段、25 个内部扩展字段**；
- 核心表单字典共有 **5 个表单族**；
- 标准字段编号、内部扩展列名在各自分组内没有重复。

这一方向应保留，但还需要增加唯一性、来源映射和跨文件一致性校验。

### 3.2 部分技术修正方向正确

- 双哈希分离模型能够避免将最终文件自身摘要写入自身所造成的自引用问题；
- 150MB 字节硬配额比单纯的文件数量限制更符合微信端存储约束；
- 区分正常离线排队与设备时钟异常的方向合理；
- 架构 v1.1 已将 FastapiAdmin 用户状态修正为 **`0=启用、1=停用`**；
- 架构 v1.1 已明确调阅和出证时执行全文件 SHA-256，而非以 ETag、CRC64 或抽样哈希替代；
- `TC-SYS-04` 已体现受控代管、默认只读、敏感操作二次授权及原始证据禁改的正确方向。

### 3.3 表单标准表号纠偏有效

以下表号修正可以认可：

- 旁站记录：`GB/T 50319-2013 表 A.0.6`；
- 监理通知单：`表 A.0.3`；
- 工程暂停令：`表 A.0.4`；
- 监理通知回复单：`表 B.0.5`；
- 专项施工方案报审：`表 A.0.1`。

需要注意：**表号纠偏完成不等于表单业务闭环已经完成。**责任主体、签认、送达、版本和工序门禁仍需单独验收。

## 五、必须优先解决的阻断问题

### 5.1 P0：节点种子库与唯一键模型直接冲突

对 `hazard_nodes_seed.json` 的实际复算结果如下：

| 检查项 | 结果 |
|:---|---:|
| 节点记录总数 | 347 条 |
| 不同 `node_code` 数量 | 244 个 |
| 出现重复的编码数量 | 31 个 |
| 因重复产生的额外记录 | 103 条 |

典型案例：

- `A-04-01` 同时对应专项方案、资质审查、悬挑型钢、吊篮悬挂机构、卸料平台等 6 种不同业务含义；
- `A-03-01` 同时对应方案论证、整机资质核验、安拆配件验收；
- `A-02-01` 在不同模板工程子类别中重复出现。

PRD 第 6.1.1 节第 1435 行却将 `node_code` 定义为 `UK` 唯一键。**按当前数据导入将直接发生唯一键冲突。**

问题根因是原始清单在不同子类别中重新从 1 编号，而种子库没有保留子类别和原始表格定位。

整改要求：

1. 增加 `subcategory_code` 或等效的子体系标识；
2. 保留 `source_document`、`source_table_id/index`、`source_row_no`；
3. 重新制定全局稳定、唯一、可版本化的节点身份编码；
4. 区分内部主键、对外业务编码和原始清单序号；
5. 将唯一性检查纳入自动生成和 CI，不得仅校验总记录数。

同时，第 12 类是 5 个通用场景，与专业工序条目的粒度不同。**347 当前更准确地说是 347 条基线记录，不宜未经业务确认即等同于 347 个同质化工序节点。**

### 5.2 P0：原始材料的空白与错误未得到正确治理

回查原始 A-8 清单发现：

- “现场焊接探伤过程管控”未标注 ★/△；
- “构件安装变形隐患巡视闭环”未标注 ★/△；
- 种子库却将二者直接补为 `△`，见 JSON 第 4489、4505 行附近。

这属于未经确认的规则补值，不能称为严格继承原始材料。应保留 `UNSPECIFIED`、`PENDING_REVIEW` 等状态，并进入人工确认清单。

原始 A-2 也存在自身内容错误：“混凝土浇筑与监护”的监理履职文字实际为“爬升后架体固定与维护”的内容。种子库继承了该错误，说明还需要源数据业务校审。

整改要求：

- 原始材料错误应登记、确认和修订，不能静默继承或静默修正；
- 任何风险等级、采集频率和强制要求的补值，都应记录决策人、依据、时间和版本；
- 建立“原始值、规范化值、差异原因、审核状态”四类追溯信息。

### 5.3 P0：超管与离线规则在正文中仍然冲突

典型残留包括：

- 第 665 行仍画有“超管 PC＋微信小程序”；
- 第 714、1513 行仍要求超管绕过租户过滤、放行全量数据；
- 第 1060 行仍授予超管跨租户修改、审批和干预权限；
- 第 2103～2105 行仍允许超管访问小程序审核、隐患和审批页面；
- 第 950、1177、1888、2212、2547、2565～2566 行仍执行 50 张照片/5 段视频，与 150MB 方案冲突。

特别需要明确：**二次授权只是平台安全控制，不会使超管自动取得总监或专监的岗位资格。**代管可以支持受控调阅和导出，不宜默认支持其代替法定责任人完成审批或终审。

### 5.4 P0：字段字典与 PRD 仍不是同一契约

| 字段 | 当前冲突 |
|:---|:---|
| B301 | 字典使用 `file_sha256`；PRD ER、附录和 JSON 示例使用 `sha256_hash`。 |
| B010 | 第 1538 行为 20 字；功能页和字典为 50 字。 |
| B104 | 第 1551 行为 `VARCHAR(100)`；字典为 `VARCHAR(200)`。 |
| B304 | 第 1576 行为 `VARCHAR(255)`；字典为 `VARCHAR(512)`。 |
| B011 | 第 1539 行写服务端生成；字典写端侧离线生成、服务端校验。 |
| B003 | 种子库应急节点使用 `99`；PRD ER 和字段表仍只写 `01/02/03`。 |
| B001 | 正文使用住建备案/TJ 编码；`TC-SYS-02` 仍生成 `PRJ-ENT001-...`。 |

因此，“全栈统一使用 `snake_case`、机器字典为唯一事实来源”目前仍只是声明，尚未兑现到 PRD 自身。

### 5.5 P0：严重隐患和验收门禁尚未形成可执行闭环

依据住建部令第37号：

- 第十九条规定，情节严重时监理单位应要求暂停施工并及时报告建设单位；施工单位拒不整改或不停止施工时，应及时报告建设单位和工程所在地住房城乡建设主管部门；
- 第二十一条规定，验收合格并经施工单位项目技术负责人及总监理工程师签字确认后，方可进入下一道工序。

当前 PRD 仍主要停留在“一般/重大隐患＋48 小时升级督办”，缺少：

1. 停工签发、停工范围、签发人、送达及拒收记录；
2. 报告建设单位、主管部门的对象、时间、文号、附件和签收凭据；
3. 拒不整改、拒不停工的独立事件流；
4. 复工申请、复工条件及审查记录；
5. 通知回复、复查人、复查时间和多轮复查记录；
6. 旁站双方签认及验收双签；
7. 验收合格和标识公示完成后的下一道工序门禁。

普通整改的 48 小时催办可以保留，但不能替代严重隐患的即时处置规则。

## 六、高优先级完善事项

### 6.1 P1：重复任务与版本快照仍只停留在整改声明

`building_zone`、`batch_no` 和“不适用剔除”等规则主要出现在第 0 章核销表，未完整进入 ER、任务状态机和页面规则；第 1282 行仍采用旧的“实采节点数÷应采节点数”公式。

应补齐：

- 危大实体或部位实例；
- `occurrence_id`、楼栋/部位、施工批次；
- 节点及专项方案版本快照；
- 不适用申请与审批；
- 一任务多图、多视频的完成条件；
- 驳回、重拍、历史作废及并发审核规则；
- 已进入施工时点的应采任务分母算法。

### 6.2 P1：容量和性能指标仍不可直接验收

- 第 1866 行仍写年增量 2～5TB，没有采用核销表的新测算；
- 产品回复中的“10～20 项目年增量 1.5～4.5TB”不能由原公式直接推出；
- 按原假设复算，10～20 个项目年增量区间约为 **0.803～5.84TB**；
- 水印性能仍有 300ms 与 800/1500ms 两套标准；
- 单图上传、原图加载等也存在不同阈值；
- “100 人在 5 分钟内上传”与“100 路同时上传”不是同一负载模型。

应统一测试机型、网络、数据量、并发模型、耗时起止点及 P95/P99 指标。

### 6.3 P1：隐私与数据合规专节未实际落地

产品回复宣称新增个人信息保护专节，但 PRD 正文未形成完整规则。系统涉及手机号、人员证件、人脸影像、定位轨迹、设备标识及审计快照，应补充：

- 处理目的、范围和最小必要清单；
- 告知、授权及敏感个人信息处理规则；
- 保存期限、删除、更正和导出机制；
- 委托处理、跨主体调阅及超管代管的授权依据；
- 脱敏、访问控制和泄露处置；
- 个人信息保护影响评估及试点前合规审查。

### 6.4 P1：生成过程尚不可复现

PRD 引用的 `scripts/generate_baseline_data.py` 当前仓库中未找到。应将生成脚本、依赖、运行命令、输入文件版本和校验报告纳入仓库，避免只交付结果文件而无法复现。

## 七、再次提交评审的准入条件

建议产品负责人组织完成以下事项后，再申请开发基线复审：

1. **发布统一的 PRD v2.2**：同步清理正文、ER、页面、用例和更新摘要中的旧规则，而不是只修改第 0 章。
2. **重建节点身份模型**：保留原始表格、子类别和行号，解决全部重复编码，区分基线记录与同质化工序节点。
3. **完成源数据校审**：空白风险等级不得擅自补值，原始内容错误须登记并经业务确认。
4. **纳入可复现生成链路**：提交生成脚本及 CI 校验，覆盖数量、唯一性、枚举、阶段、风险等级和原始行映射。
5. **统一字段契约**：由字段 JSON 生成 PRD 表格、SQL、API Schema 和测试契约，消除所有跨文件漂移。
6. **补齐法定履职状态机**：形成严重隐患、停工、送达、报告、复查、复工和验收工序门禁的完整规则。
7. **统一非功能指标**：重新核算容量，统一性能、兼容性和验收口径。
8. **完成关键技术 PoC**：验证真机离线容量、重启恢复、后台续传、时钟校验、全文件 SHA-256、OSS 保留策略及双租户越权。
9. **完成隐私与法务专项复核**：清理绝对化证据效力措辞，补齐个人信息保护规则。

## 八、最终意见

本轮修改具有实质进展，尤其是机器可读基线、双哈希模型、离线配额、认证状态及表单表号等方面。但当前问题已不再只是文字润色，而是涉及：

- 数据库能否导入；
- 权限边界是否唯一；
- 原始数据是否忠实；
- 法定职责能否闭环；
- 验收指标能否执行。

因此，建议将当前版本的“评审闭环正式版”定位调整为“评审整改中版本”。**在完成本报告第七部分准入条件前，不建议全量开发或对外宣称全部问题已经核销。**
