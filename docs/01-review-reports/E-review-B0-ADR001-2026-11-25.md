## 一、总评

1. **红线核验（两代理一致确认）**：TenantCRUDBase＋ORM 钩子双防线严密（伪造 tenant_id 拒绝、无上下文 fail-closed、代管只读强制）；TENANT_OWNER/TENANT_ADMIN/SZ/SP/SA 零写入 `sys_user_roles`；单持有人模型＋固定锁序（先锁成员行后改 Owner 行）＋version 乐观锁在 READ COMMITTED 下防双/零 Owner 有效；全部裸 SQL 参数化、无跨租户越权与提权可达路径；审计同事务 append-only。
2. **验证声明核验（AST 解析，100% 相符）**：后端 648＋真实 MySQL 行锁交错 7＝655 用例、前端 Vitest 49，与 `dfdc6cc` 提交说明完全一致；"E2E 17/17"为本地真实环境手工/浏览器探针记录，对应 API 场景已固化为自动化回归（`test_tenant_platform_api.py`/`test_tenant_adr001.py`）。测试设计达生产级水准（可控交错 Session 包装器、迁移三方言渲染、PG 序列同步）。
3. **附条件原因**：发现 2 Major 边界缺陷＋1 High 配置风险（合并前必修）＋1 Medium（小程序生产前必修）＋若干加固项；**均属局部补强，不推翻数据模型、迁移链或 API 契约**，不阻塞产品交接与统一口径发布。

## 二、合并 main 前必改条件（修复＋复验后合并）

| # | 来源 | 严重度 | 问题 | 修复要求 |
| :--: | :--- | :---: | :--- | :--- |
| C1 | 质量 F-01 | Major | 多租户账号（或兼属冻结租户的平台移交专员）缺省 `X-Tenant-Id` 时取 `members[0]` 未过滤冻结租户：首租户冻结即连正常租户也无法访问；平台专员在 `current/info` 路由守卫阶段被清退，浏览器端无法执行兜底移交 | `_authenticate` 与 `get_first_active_member` 优先选取未冻结租户的最早有效成员（全部冻结才回退拦截）；平台权限账号走公共自查接口时不清退会话；补多租户冻结场景单测 |
| C2 | 质量 F-02 | Major | `POST /system/user/import/data` 批量导入更新绕过现任 Owner 停用保护（update/delete/set_available 三入口有守卫，导入路径漏防，可产生"账号已停用的在任 Owner"） | `_process_import_row` 在 `status=1` 时接入 `_reject_if_current_owner`＋写后 `_assert_no_owner_after_write`；补单测 |

## 四、后续迭代加固项（不阻塞，排入 B0 收尾或 B1）

安全：E2-03 租户成员/项目列表无权限门控（新成员可枚举全员登录名，与 E4 叠加扩大撞库面）；E2-05 平台权限撤销不即时生效（会话快照 7 天滑动窗口内仍可移交）；E2-06 会话清退用 Redis KEYS 全库扫描（大租户可用性抖动）＋purge 吞错静默失败（改 SCAN＋告警）；E2-07 种子双超管同默认口令；E2-08 匿名注册/小程序码无限流。
质量：F-05 租户侧两个列表 2N+1 查询；F-06 清退与 commit 时序不一/停用未判 `is_deleted`/裸 SQL 未刷 `updated_time`；F-07 `GET /projects/{id}/members` 兼任 `require_project_role` 探针（B1/B3 落地业务接口时解耦）；F-08 `_grant_admin`/`assign` 未校验底层 `sys_user` 状态；F-09 前端 `admin_mode` 类型残留 `"none"`。
