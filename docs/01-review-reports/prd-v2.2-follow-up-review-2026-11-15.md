## 五、主要阻断问题

### 5.1 P0：结构 `PASS` 不能代替业务基线准入

当前只有 **16 条节点为 `CONFIRMED`**，其余 **331 条节点为 `PENDING_REVIEW`**。

但 PRD 同时存在以下规则：

- 第 5.3 节要求自动加载全部标准节点生成任务；
- 小程序和节点管理页面主要展示 ★/△，未形成完整的源数据校审工作流；
- `applicable_status` 未明确处理 `PENDING_REVIEW`；
- 第 10.1 节要求基线库只读，但又需要业务专家批量确认风险等级；
- 新的完整度算法没有明确排除全部待校审节点。

因此，`validation_report.json` 的 `PASS` 只能解释为：

> **记录数量、字段数量和节点 UID 唯一性通过。**

不能解释为：

> **源数据已审定，全部节点均可用于正式强制采集和履职完整度考核。**

建议将验证状态拆分为：

- `structural_status=PASS`
- `source_review_status=PENDING`
- `business_readiness=BLOCKED`

同时建立待校审队列、审核人、审核依据、审核时间、处理结论和版本记录。

### 5.2 P0：生成脚本实际能力低于文档宣称范围

脚本第 243 行只有一个节点 UID 唯一性断言，第 348 行直接写入 `status: PASS`。

当前脚本没有：

1. 读取或生成 PRD；
2. 校验 PRD 旧规则残留；
3. 校验字段名称、类型和长度是否与 PRD 一致；
4. 校验 PRD 示例节点是否真实存在；
5. 校验示例风险等级与种子库是否一致；
6. 校验命名公式是否一致；
7. 校验待校审节点是否被错误纳入正式任务；
8. 校验权限、性能和验收用例之间的冲突。

因此：

- “PRD 全部由脚本生成”目前不成立；
- “CI 字段契约和全文残留断言已落实”目前不成立；
- “生成结果可复现”成立，但不能扩展为“完整 SSOT 与 CI 已闭环”。

### 5.3 P0：PRD 示例数据存在明确错误

对 PRD 中两个 JSON 示例逐一回查节点库：

| 示例 | 示例内容 | 种子库实际情况 |
|:---|:---|:---|
| 示例一：`WDGC-A-01-SC01-25` | 写为 ★ | 节点存在，但实际为 `UNSPECIFIED + PENDING_REVIEW`。 |
| 示例二：`WDGC-A-04-SC01-18` | 写为 ★ | 该 `node_uid` 不存在；落地式脚手架 `SC01` 只有 12 条记录。 |

这证明当前校验未覆盖“PRD 示例必须引用真实节点且状态一致”的基本要求。此类示例不能直接交给开发或测试使用。

### 5.4 P0：标准字段语义与正文仍未统一

#### B004：全局身份与原始标准编号混用

原 B004 的标准语义是附录清单节点编号。新增 `node_uid` 应作为内部全局身份扩展，或经正式标准变更后重新定义交换标准，不宜直接把 B004 改成另一种含义。

建议分别管理：

- 原始/兼容业务编号：`legacy_node_code`；
- 内部全局身份：`node_uid`；
- 子类别：`subcategory_code`；
- 原始来源定位：文档、表格和行号。

#### B005：风险等级与校审状态混用

`UNSPECIFIED` 表示源数据待确认，不是与 ★/△ 同级的业务风险等级。建议通过 `review_status` 和待定值/空值分别表达，避免将待审状态写入正式风险等级标准。

#### B006：节点建议介质与单文件介质混用

单个影像文件的 `media_type` 应是“照片”或“视频”；“照片+视频”适合节点级的 `suggested_media_type`，不适合单文件证据记录。

#### 其他跨文件冲突

| 字段/规则 | 当前残留问题 |
|:---|:---|
| B010 | 第 1591 行仍为 20 字，字典为 50 字。 |
| B104 | 第 1604 行仍为 `VARCHAR(100)`，字典为 200。 |
| B011 | 第 1592 行仍写服务端生成，字典为端侧生成、服务端校验。 |
| B304 | 第 1629 行仍为 `VARCHAR(255)`，字典为 512。 |
| ER 节点字段 | 第 1491 行仍使用 `node_code`，未统一为 `node_uid`。 |
| ER 风险字段 | 仍写 `CHAR(1)`，无法容纳 `UNSPECIFIED`。 |
| ER 阶段字段 | 仍只写 `01/02/03`，未覆盖应急节点 `99`。 |

### 5.5 P0：命名公式与权限规则仍不一致

种子库的命名公式包含：

`project + hazard + subcategory + stage + node_uid_suffix + risk + time`

PRD 第 1718、2934 行仍使用：

`project + hazard + stage + legacy_node_code + risk + time`

继续使用非唯一的 `legacy_node_code`，会重新引入文件命名歧义。应统一全链路命名规则，并增加唯一性测试。

权限方面，第 1083 行已明确“超管不得代替法定责任人签字”，但以下规则仍冲突：

- 第 538 行允许超管二次授权后跨项目审批/驳回；
- 第 568 行保留“代管二次授权后终审”；
- 第 737 行仍写“放行全局穿透过滤、允许跨租户管理全量数据”。

二次授权只是平台安全控制，不等于法定岗位授权。上述规则需要继续清理。

### 5.6 P1：新增法定闭环缺少对应验收用例

严重隐患、报告主管部门、复工和验收门禁虽然进入正文，但现有 `TC-REV-01～04` 仍主要覆盖普通审核、双图和 48 小时督办，没有完整覆盖：

- 严重隐患停工及送达；
- 建设单位报告及签收；
- 拒不整改/拒不停工时报告主管部门；
- 多轮复查；
- 复工申请与审查；
- 验收双签、公示及下一道工序解锁。

没有这些用例，不能把状态机文字补充直接视为可验收闭环。

### 5.7 P1：性能和技术能力口径仍需收敛

- 水印性能仍有 300ms 与 800/1500ms 两套标准；
- 单图上传仍有 3 秒与 2 秒两套标准；
- 原图加载仍有 2.5 秒与 1.5 秒两套标准；
- 第 1188 行仍承诺提取完整相机厂商、焦距、快门等 EXIF；
- `TC-SEC-04` 仍将 Fake GPS 识别和阻断作为确定性能力，需等待真机验证；
- iOS、浏览器和部署隔离术语仍有历史口径残留。

上述事项应与真机 PoC 结果统一，不宜继续以绝对承诺方式写入验收基线。

## 六、下一步整改顺序

1. **先完成 332 项源数据校审**：明确每条风险等级和处理依据，未确认节点不得进入正式强制采集任务及完整度考核。
2. **重新划分标准字段与内部扩展字段**：重点处理 B004/B005/B006，避免标准语义被内部技术实现覆盖。
3. **修正 PRD 示例、ER 和命名公式**：所有示例节点必须真实存在，风险状态与种子库一致。
4. **扩充生成脚本和 CI**：自动检查 PRD 字段、示例 UID、风险状态、权限旧词、命名公式及待审节点使用边界。
5. **拆分结构验证与业务准入**：验证报告分别输出结构状态、源数据校审状态和业务就绪状态。
6. **补齐严重隐患及验收门禁测试用例**：统一权限、性能和兼容性口径。
7. **完成真机与云服务 PoC**：验证离线容量、重启恢复、后台续传、时钟、全文件 SHA-256、OSS 保留策略及双租户越权。
8. **完成法务与隐私专项复核**：确认个人信息处理依据、敏感信息规则、跨主体调阅和超管代管边界。

## 七、最终意见

PRD v2.2 相比 v2.1 已有明显进步，尤其是：

- 唯一节点身份模型；
- 可复现生成链路；
- 原始空白值不擅自补值；
- 法定履职状态机与 Occurrence 模型；
- 隐私合规专节。

但当前仍存在三类未闭环：

1. **业务未闭环**：331 条节点风险待审，另有 1 条原始内容错配待审；
2. **契约未闭环**：PRD 示例、字段、ER、命名和权限仍与新版字典不完全一致；
3. **验证未闭环**：CI 覆盖有限，真机与法务复核尚未完成。

因此，**v2.2 可以继续作为整改工作底稿和有限技术 PoC 输入，但不能签收为全量开发基线。**
