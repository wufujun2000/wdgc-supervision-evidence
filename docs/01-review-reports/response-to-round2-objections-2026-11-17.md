## 二、第4章专项异议逐项裁定

### 异议 A：第4章仅 35 行、架构图与业务流转图灭失 —— **裁定：成立，采纳恢复**

**事实确认**：原 v1.0 第 4 章约 402 行，含 6 层分层架构图与端到端业务全景流转图；v2.4 第 4 章仅 35 行文本条目。总体设计章节失去图形化骨架，确实影响研发、测试对系统数据流向与模块协作的理解。这与我方 v2.3 复审"摘要化导致可执行契约丢失"的既有批评同源，采纳。

**对两张 Mermaid 图的内容核验**（采纳前核对与 v2.4 契约的兼容性）：

- **6 层架构图**：`TenantCRUDBase` 强制注入租户过滤、双哈希引擎、五级目录映射、Append-Only 审计——与 v2.4 契约及双方铁律一致，兼容；
- **端到端流转图**：Occurrence 任务实例、150MB 离线沙箱、原始帧水印→服务端 `file_sha256` 固化、监理登记回复单 + `_HW` 复查照片、总监审批闭环——与 v2.4 一致，兼容。

**采纳方式**：两张图在术语对齐（节点身份展示、Occurrence、双哈希命名与 v2.4 一致）后，补入融合版 PRD 的第 4 章；架构侧同步在 `docs/03-architecture/system-architecture-design.md` 中引用同一图源，避免两处维护产生漂移。

### 异议 B：解耦 FastapiAdmin、改用原生 FastAPI 重写 —— **裁定：风险关切合理，解耦诉求不采纳**

**异议中成立的技术关切**：小众开源项目的维护生命周期、供应链稳定性、未来政企/信创环境适配，这些是真实且值得登记的风险项。

**但异议的技术论证存在概念混淆，需要澄清**：

1. **FastapiAdmin 不是与 FastAPI 并列的另一条技术路线**——它本身就是基于 FastAPI + SQLAlchemy 2.0 + Pydantic v2 的应用脚手架。"改用原生 FastAPI + SQLAlchemy 2.0 + Pydantic v2"与"使用 FastapiAdmin"不是二选一：当前工程用的正是这套标准栈，FastapiAdmin 提供的是骨架代码而非替代性运行时。
2. **信创适配的关键点不在框架**：达梦/人大金仓的适配主要取决于 SQLAlchemy 方言与 SQL 写法（应在数据访问层做方言抽象与禁方言特性清单）；统信/麒麟 OS 属于部署环境；国密 SM2/SM3/SM4 属于传输与密码层——三者都与"是否使用 FastapiAdmin"基本正交。
3. **推翻成本与既成事实**：FastapiAdmin 原生基线已完成导入（1,182 个文件）并通过真实 MySQL/Redis、接口、登录、权限、CRUD、Nginx、移动 H5 的运行验收（`docs/05-verification/fastapiadmin-baseline-acceptance.md`）。此时推翻重写，是把已验证资产换成未验证重写，风险方向相反。

**替代方案（工程约束清单，作为架构决策记录提交技术负责人最终裁决）**：

| 约束项 | 内容 |
| :--- | :--- |
| 供应链自持 | 锁定完整 commit + `vendor/` 本地留存 + 关键模块自研增强（架构文档既定策略），不依赖上游持续维护即可独立演进 |
| 代码侵入隔离 | 业务代码集中于 `src/` 应用层；对基线的修改以补丁/扩展形式登记，禁止大面积改写 vendor 原生代码导致无法比对升级 |
| 数据库方言抽象 | 数据访问层禁用 MySQL 方言专属特性清单化，为未来达梦/金仓适配预留方言层（列入技术债登记，非一期任务） |
| 国密与信创登记 | 国密算法、国产 OS 适配登记为未来扩展项，在网关/传输层评估，不作为当前重写理由 |

**裁决建议**：维持现有选型，以上述工程约束回应风险。最终拍板权属于技术负责人（架构决策属其职权，非第三方评审可单方推翻），建议以架构决策记录（ADR）形式留痕。

### 异议 C：受控代管补齐脱敏、防泄密水印、会话时效 —— **裁定：全部采纳**

与 v2.4 第 7.7 节个人信息保护方向一致，属于对既有规则的必要细化，无争议。采纳时做两处精确化：

1. **动态脱敏**：代管会话内手机号、证件号默认掩码（如 `138****1234`），明文查看需二次授权并单独记审计；
2. **全屏威慑水印**：代管期间全屏半透明动态水印（超管工号 + 时间 + 目标租户编码），定位为**威慑与泄密追溯**，不宣称技术上能阻止截屏/录屏；
3. **会话时效**：默认 ≤30 分钟硬超时（可配置收紧、不得放宽），超时强制登出，一次性授权码不得复用。

## 三、汇总确认版的确认与口径修正

**确认部分**：

- 7 项技术铁律（终端架构、双哈希、150MB、租户行级隔离、超管边界、施工方边界、标准表号）——双方一致，本评审方认可为定稿口径；
- "一后端三前端"异议经双方研讨正式撤销——记录为争议闭环，不再回议；
- 异议 1（正文定性回填）、异议 4（简洁业务编号展示）、异议 5（验收门禁措辞精确化）——维持第一轮回应裁定，不再重复展开。

**必须修正的两处口径**（避免在执行中再次跑偏）：

1. **"把 business_readiness 由 BLOCKED 解锁"不是数据回填的直接结果**。BLOCKED 是六维综合门控（结构、静态一致性、源数据校审、技术 PoC、合规复核、行为验收），回填只解决"源数据校审"一维。回填完成后的正确效果是：**映射成功的节点转为 CONFIRMED 并进入任务分母**，`source_review_status` 按实际映射结果更新；其余维度仍按验证清单并行推进。它们本来就不阻塞开发与原型，无需以"解除 BLOCKED"为目标牵引动作。
2. **"以分章 PRD 为唯一事实源"应改为"以融合版 PRD 为业务详述、以 v2.4 为数据契约基线"**。v1.0 中含有大量双方已共同确认废弃的错误内容（哈希自指、550MB 配额、超管全量放行、错误表号等），不能简单"以 v1.0 为准"整体回滚。唯一可行路径是**融合**而非**回滚**。
