## 一、执行摘要

v2.3 相比 v2.2 有实质进步：新增真实 PRD 生成器和一致性校验脚本，明确区分结构状态、源数据校审状态和业务准入状态；`node_uid`、字段语义、真实节点引用、业务准入门禁及法定履职用例均有改善。

本次在当前目录直接执行以下完整链路：

```bash
python3 scripts/generate_baseline_data.py
python3 scripts/generate_prd_v23.py
python3 scripts/validate_prd_consistency.py
```

实际结果：

- 347 条节点记录、347 个唯一 `node_uid`；
- 16 条 `CONFIRMED`、331 条 `PENDING_REVIEW`；
- 37/37 项脚本校验通过；
- 重跑后受 Git 管理的文件无差异，证明当前生成结果可复现。

但 **37/37 通过只能证明脚本当前覆盖的 37 项条件成立，不能证明 PRD 全部正确**。本轮在校验之外仍发现法规表号错误、架构旧规则残留、示例跨类别错配、PRD 扩展列数量错误，以及核心业务验收深度不足。

因此建议：

1. 认可 GitHub 协作、SSOT 生成和业务准入状态拆分的整改方向；
2. 继续保持 `business_readiness=BLOCKED`，不得把 37/37 作为全量开发签收依据；
3. 允许开展限定范围的技术 PoC、源数据业务校审和文档修订；
4. 修复本报告 P0 项后，再提交下一轮基线复审。

## 三、P0：再次提交开发基线前必须修复

### P0-01：GB/T 50319-2013 表号映射存在明确错误

**位置：**

- `docs/prd/PRD_v2.3_评审整改中.md` 第 191、195、221、338、385～386 行；
- `docs/baseline-data/metadata_and_forms_dictionary.json` 的 F04、F05；
- `docs/architecture/system-architecture-design.md` 第 256 行。

**当前错误与正确映射：**

| 表单 | 当前文档 | 正确表号 |
| :--- | :--- | :--- |
| 施工组织设计/专项施工方案报审表 | A.0.1 | **B.0.1** |
| 工程暂停令 | A.0.4 | **A.0.5** |
| 监理通知回复单 | B.0.5 | **B.0.9** |

其中：

- A.0.1 是总监理工程师任命书；
- A.0.4 是监理报告；
- B.0.5 是施工控制测量成果报验表。

监理通知单 A.0.3、旁站记录 A.0.6 的映射正确，应保留。

**影响：**表号进入 PRD、表单字典、ER、PDF 版式和验收用例后，会造成法定单据模板与责任主体错配。该项不是文字瑕疵，必须优先修复。

**核验依据：**

- 住建部《建设工程监理规范》发布公告：<https://www.mohurd.gov.cn/gongkai/zc/wjk/art/2015/art_17339_224529.html>
- GB/T 50319-2013 基本表式目录：<https://www.jianshe99.com/jianli/bkzl/wa20210303175657.shtml>

### P0-02：架构文档仍保留已被 PRD 否决的旧契约

`validate_prd_consistency.py` 只读取 PRD v2.3，没有校验架构文档，因此以下冲突不会影响 37/37 结果：

1. **扩展列数量冲突**：PRD 第 18 行和架构第 156 行写 25 个，实际字典、README 和验证报告均为 **28 个**。
2. **命名公式冲突**：PRD 第 235 行已使用 `subcategory_code + node_uid_suffix`；架构第 158～163 行仍使用旧 `node_code` 公式。
3. **任务模型冲突**：PRD 使用 `biz_task_occurrence`；架构第 99、179 行仍以 `biz_task_instance` 为核心任务模型。
4. **超管权限冲突**：PRD 第 115、128 行禁止超管代替法定责任人审批；架构第 116、118、125 行仍保留代管后“审批”能力描述。
5. **架构过度承诺仍在**：架构第 21 行仍写 ORM 层“100%”隔离和未来分区“业务层零改动”，不能覆盖裸 SQL、关联预加载、Worker、Redis/OSS 及 MySQL 分区约束。

**整改要求：**把架构文档纳入同一 CI 校验范围，或由同一 SSOT 生成相关章节；不能仅修 PRD、保留架构旧正文。

### P0-03：“真实示例”存在跨类别、跨阶段和节点错配

**位置：**`scripts/generate_prd_v23.py` 第 25～38 行；生成后的 PRD 第 455～485 行。

示例一的真实节点为：

- `node_uid=WDGC-A-08-SC01-01`；
- 08 钢结构、SC01、01 施工准备阶段；
- 节点名称为“钢结构吊装、索膜张拉专项方案编审与专家论证”。

但示例的 `storage_path` 却硬编码为：

- `01_基坑工程`；
- `03_分部分项验收阶段`；
- 文件名使用 `01_SC01_03_25`，既不是 08 类，也不是当前节点后缀 01；
- `position_desc` 仍为“1#楼北侧坑底”，与钢结构方案编审节点不匹配。

此外：

- `risk_summary` 通过 `[:40]` 截断，正文以“构件失”结束，语义不完整；
- `raw_frame_sha256` 使用空字节串的常见 SHA-256 值 `e3b0c442...b855`，不应表现为真实现场帧摘要；
- 文件哈希、时间和位置均为演示数据，应明确标记“合成示例”，不能与“真实节点”混称为真实证据。

**整改要求：**示例所有分类、阶段、目录、文件名和部位字段均由同一节点派生；增加跨字段一致性断言；风险简述不得按字符硬截断；合成哈希必须显式标记为演示值。

### P0-04：37 项 CI 未覆盖其宣称的关键正确性

当前校验脚本主要是数量、关键词和少量字段等值检查，尚未覆盖：

- 标准表号正确性；
- PRD 首页扩展列数量；
- 架构文档旧规则；
- 示例存储路径与节点分类、阶段、子类别、后缀的一致性；
- PRD 字段表与字典逐行完全一致；
- 风险状态与任务生成的可执行约束；
- 隐患和验收状态机的合法/非法转换；
- 非法越权、并发审核、重复上传和失败补偿等行为测试。

`prd_consistency_report.json` 中部分成功项的 `detail` 仍写“存在重复 node_uid”“缺少 TC-REV-05”等失败提示，虽然 `passed=true`，但容易误导审阅者，应分别输出成功与失败说明。

**结论：**37/37 是真实脚本执行结果，但不是完整业务正确性证明。报告名称建议限定为“静态一致性校验”，不要扩大为“全量开发准入校验”。

## 四、P1：业务与原型阶段必须继续补齐

### P1-01：已确认节点不足以支撑原定 MVP 试点

347 条记录中只有 16 条 `CONFIRMED`：

- 08 钢结构：11 条；
- 12 通用应急：5 条；
- 其余 10 个专业类别均为 0 条。

因此，目前不能按已确认节点直接开展基坑、脚手架等原定完整专业闭环试点。继续维持 `BLOCKED` 是正确的，但应补充：

- 业务校审责任人、依据、完成条件和版本生效规则；
- 每个 MVP 类别的最小确认节点集；
- 校审后种子版本升级及既有 Occurrence 快照迁移规则；
- 16 条已确认节点是否本身也经过业务专家签认的证据。

### P1-02：PRD 从详细规格缩减为摘要，部分可执行契约丢失

v2.3 仅 527 行，功能章节多采用单条项目符号。相比前版，以下细节不足：

- 任务、影像、隐患、停复工和验收的完整状态枚举及转换条件；
- 各状态允许角色、前置条件、副作用、通知、审计和异常回退；
- 重复提交、并发审核、上传失败、OSS 成功但数据库失败等补偿规则；
- 表单逐字段责任主体、签认方式和版本关系；
- 关键页面交互、空态、错误态、权限拒绝态及离线冲突处理；
- 容量规划、租户配额、导出限流和运维告警。

“法定履职全闭环”目前更接近“关键名词和高层用例已覆盖”，尚不是可直接开发测试的完整状态机规格。

### P1-03：危大分类表述仍需去法规化误读

PRD 第 60 行称危大工程依 37 号令“包含 12 大类”，但当前第 12 类是课题补充的通用应急模块，不是与 11 类专业危大同质的法定类别。

建议统一写成：**“11 类专业危大课题清单 + 1 个通用应急兜底模块，共 347 条基线记录。”**

### P1-04：非功能指标仍需要可验证边界

- 第 262 行“纯离线业务可用度 100%”未定义功能范围，与登录、授权、同步及 150MB 配额限制不完全相容；
- 单图上传 2 秒、60MB 视频 20 秒、证据包 4GB 五分钟等缺少带宽上下限、服务端处理起止点和失败重试口径；
- 主包 1.5MB、连续拍摄内存 350MB、后台恢复和原始帧 SHA-256 均须真机 PoC；
- 架构仍使用 300～800ms 水印描述，PRD 为 800/1500ms，需统一测试口径。

### P1-05：留存、销毁与原始证据禁删之间需要统一

第 242 行允许常规影像到期审批后清理，第 243 行又规定原始取证文件严禁任何角色物理删除。需明确：

- 原始文件、衍生文件、临时缓存和导出副本分别适用什么规则；
- 到期销毁、法定/争议保全 `legal_hold`、匿名化和逻辑删除的优先级；
- 销毁后保留哪些清单、哈希和审批证据；
- 留存期限属于法规、合同、课题建议还是企业政策，并记录依据版本。
