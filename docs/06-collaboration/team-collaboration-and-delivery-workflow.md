## 一、目的与适用范围

本规则用于统一四个团队的任务边界、并行工作方式、交付物、变更沟通和验收准入，避免以下问题：

- 产品团队反复修改 PRD，技术团队长期无法进入真实开发；
- 技术团队根据不完整需求自行猜测业务规则；
- 原型、数据库和 API 各自演进，直到联调时才发现冲突；
- 测试团队在开发完成后才介入，导致异常流程和权限问题集中返工；
- 专家评审范围不断扩大，以文档审查代替真实产品验证。

本规则适用于本仓库及后续前后端工程、数据库、测试和评审活动。各团队应在保持各自专业职责的前提下，按本规则协同推进。

## 二、核心原则

### 2.1 需求稳定即可开发，不要求 PRD 完美后才开始

核心业务对象、主要角色和首条业务链明确后，技术团队即可搭建真实基线并开展开发。局部字段、页面交互和后续节点库可以在开发中受控完善。

不得因全部节点尚未校审、部分页面尚未定稿或非核心文档存在一般问题，而暂停整个项目。

### 2.2 产品不设计底层，技术不猜测业务

- 产品负责人不需要决定数据库字段类型、索引、框架或底层实现；
- 技术负责人负责把业务需求转化为架构、数据库、API 和代码；
- 技术团队发现业务规则缺失时，必须提出具体问题，不得静默发明业务规则；
- 涉及监理法定职责、签认主体和强制采集要求时，由业务专家确认。

### 2.3 并行推进，不等于相互脱节

产品原型、技术基线、业务校审、测试设计和专项 PoC 可以并行。各团队不需要实时同步所有工作细节，但涉及业务对象、状态、权限、字段必填性和接口规则的变化必须及时同步。

### 2.4 先打通一条业务链，再逐步扩展

首个开发切片建议为：

> 企业与项目 → 项目成员与权限 → 任务生成 → 现场采集 → 专监审核 → 证据查询与导出

首条链路通过联调和行为验收后，再扩展隐患、停复工、验收及其他危大类别。

### 2.5 以真实代码和测试推动需求完善

PRD、原型和架构是开发依据，但不是对实现效果的替代证明。后续评审应逐步从文字一致性检查转向真实页面、数据库、API、日志、测试记录和用户操作结果。

## 三、开发依据与事实来源

不同问题以不同交付物为准，不要求一份 PRD 承担所有技术和协作职责。

| 事项 | 主要依据 | 责任团队 |
| :--- | :--- | :--- |
| 用户目标、业务范围、角色和业务规则 | PRD、产品决策记录 | 产品负责团队 |
| 页面布局、交互和展示字段 | 原型及前端工程 | 产品负责团队 |
| 技术栈、工程结构、公共能力 | 架构设计文档及技术决策记录 | 技术开发团队 |
| 数据表、字段类型、约束、索引和迁移 | 数据模型文档、迁移脚本 | 技术开发团队 |
| 前后端接口请求、响应和错误结构 | OpenAPI/API 契约 | 技术开发团队主导，前端共同确认 |
| 监理法定职责、表单和采集专业判断 | 法规、原始材料、业务校审记录 | 业务专家/专家评审团队 |
| 功能和行为是否合格 | 测试用例、实测证据和 UAT 结果 | 测试团队、产品负责团队 |
| 试点和全量上线准入 | 业务校审、PoC、法务合规及行为验收证据 | 四方共同评审 |

同一主题出现冲突时，不得由开发人员自行选择有利版本。应建立 GitHub Issue，明确冲突、影响、责任人和最终结论，再同步修改对应交付物。

## 四、团队职责

### 4.1 产品负责团队

主要负责：

1. 对接用户，明确业务目标、使用场景和优先级；
2. 维护 PRD、角色权限的业务含义和业务流程；
3. 持续完善原型、页面和前端代码；
4. 提供页面字段、操作按钮和 Mock 数据；
5. 回答技术团队提出的业务问题；
6. 组织用户验收和业务校审；
7. 维护产品决策记录，避免口头变更无迹可查。

不负责：

- 决定数据库字段类型、索引、分布式事务或底层框架；
- 独自承诺技术可行性、性能或安全能力；
- 在未与技术团队确认的情况下频繁改变已冻结接口。

### 4.2 技术开发团队

由技术负责人统筹，后端、前端和移动端协同执行。

主要负责：

1. 按架构选型搭建并改造真实技术基线；
2. 实现多租户、认证、项目权限、审计、存储、哈希和异步任务等公共能力；
3. 根据 PRD 和原型设计数据模型、数据库迁移和 API；
4. 区分持久化字段、派生字段和前端临时字段；
5. 提供 OpenAPI、Mock 服务和接口示例；
6. 将原型前端代码接入真实 API，处理异常、加载、空态和权限状态；
7. 完成技术 PoC、性能优化和故障补偿；
8. 对技术实现作出判断，不将底层设计责任转移给产品负责人。

遇到需求不明确时，应提交具体问题及建议方案。例如：

> 驳回后是否允许重新上传？建议新增证据版本并保留原记录，是否确认？

不得仅提交“PRD 不清楚，无法开发”而没有具体问题和建议。

### 4.3 测试团队

测试团队应从首条业务链设计阶段介入，而不是等待开发完成。

主要负责：

1. 根据 PRD、原型、数据库和 API 编制测试计划；
2. 覆盖正常流程、异常流程、非法状态转换和边界条件；
3. 设计双租户越权、角色越权、并发审核和重复提交测试；
4. 验证离线、续传、哈希、WORM 和证据包离线校验；
5. 验证原型、API 和数据库字段的一致性；
6. 保存测试数据、日志、截图和报告；
7. 跟踪缺陷修复和回归结果。

测试团队不得只检查页面能否打开或接口是否返回 200，应验证业务结果和证据完整性。

### 4.4 专家评审团队

主要负责：

1. 审查重大业务、法规、架构、证据链和安全风险；
2. 对首条业务链、关键变更和上线准入进行针对性评审；
3. 区分开发阻断项、试点前必须完成项和后续优化项；
4. 提供明确、可执行的问题描述和整改建议；
5. 根据真实代码、测试和证据逐步开展行为复核。

不得：

- 以追求文档完美为目标无限扩大评审范围；
- 代替产品负责人作日常业务决策；
- 代替技术负责人完成全部数据库和接口设计；
- 在没有新增风险的情况下，对同一文档重复进行全面文字审查。

## 五、并行工作流程

### 5.1 启动对齐

并行开发前，只需完成一次轻量对齐：

- 确定首条业务链及本轮不做事项；
- 统一企业、项目、危大实体、任务、影像、单据等核心概念；
- 确定产品、技术、测试和专家接口人；
- 确定原型、API、数据库和测试交付位置；
- 建立问题与决策记录。

不得把启动对齐变成对全部 PRD 的再次全面重写。

### 5.2 产品原型线

产品团队持续开展：

- 用户访谈和需求确认；
- 页面、交互和字段完善；
- 前端代码及 Mock 数据输出；
- 加载、空白、失败、无权限和离线状态设计；
- 原型变更记录。

原型不必等待数据库完成，也不必因技术团队尚未确定全部 API 而停止。

### 5.3 技术基线线

技术团队同步开展：

- 工程骨架、认证、租户隔离、项目权限和审计；
- 数据库迁移、Redis、OSS、文件和异步任务；
- 第一版核心业务表、OpenAPI 和 Mock 服务；
- 原型前端工程接入和公共组件改造；
- 离线、哈希、WORM 和性能 PoC。

基线开发不以全部业务字段完整为完成标准，但必须具备可迁移、可测试和可扩展能力。

### 5.4 业务校审线

产品负责人组织业务专家持续开展节点和法定规则校审。校审范围与首条业务链相关的内容优先，其余节点进入后续批次。

未确认节点不得进入正式强制采集任务和履职完整度分母，但不阻塞公共框架、原型和不依赖这些节点的功能开发。

### 5.5 测试与合规线

测试团队和合规人员同步准备：

- 行为测试和越权测试；
- 真机与云服务 PoC；
- 隐私、个人信息和委托处理材料；
- 档案留存、销毁与保全规则；
- 试点 UAT 场景和证据模板。

## 六、变更沟通规则

### 6.1 可以异步定期同步的变化

以下变化通常不影响数据库和 API，可随原型提交统一说明：

- 页面布局、颜色、图标和文案；
- 按钮位置和展示形式；
- 图表样式和交互优化；
- 不改变业务含义的字段标签调整；
- 临时筛选、排序和展示偏好。

### 6.2 必须及时通知相关团队的变化

出现以下变化时，应在进入对应开发前通过 GitHub Issue 或变更记录同步：

- 新增、删除或重新定义业务对象；
- 修改字段业务含义、必填性或唯一性；
- 修改任务、审核、隐患、停复工、验收状态；
- 修改角色、数据范围或审批权限；
- 修改签认主体、法定报告或归档要求；
- 修改文件上传、哈希、留存或销毁规则；
- 修改跨表关联、租户归属或项目归属；
- 修改已冻结 API 的请求、响应或错误语义。

通知内容至少包括：变化原因、旧规则、新规则、影响页面、影响接口、建议处理方式和需要谁确认。

### 6.3 紧急业务与技术问题处理

- 产品问题由产品负责人作业务决策；
- 技术实现问题由技术负责人作技术决策；
- 法规和专业履职问题由业务专家确认；
- 跨领域问题由产品和技术负责人共同决策，必要时提交专项评审；
- 所有结论必须写入决策记录，不能只保留在即时聊天中。

## 七、原型交接与数据库字段修正

### 7.1 原型分阶段共享

不要求产品团队等全部原型完成后才交付。至少分三次共享：

1. 核心页面清单和主要业务对象确定后；
2. 首条业务链页面及 Mock 数据可用后；
3. 联调前完整原型包冻结时。

### 7.2 原型交付包内容

每次正式交接应包含：

- 可直接运行的前端工程；
- 页面路由和组件说明；
- Mock JSON 数据；
- 页面、字段和业务对象对应关系；
- 角色及操作权限说明；
- 已实现的加载、空白、失败和无权限状态；
- 本次变更和未决问题清单。

### 7.3 字段分类处理

原型中的字段由技术团队按以下规则处理：

| 类型 | 示例 | 处理方式 |
| :--- | :--- | :--- |
| 必须持久化的业务字段 | 复查人、复查时间、停工文号、验收签认 | 纳入数据模型和迁移 |
| 可计算或关联得到的字段 | 完整度、逾期状态、剩余时间 | 优先由后端计算或查询生成 |
| 仅用于前端展示的字段 | 标签颜色、展开状态、临时筛选 | 不进入业务数据库 |
| 流程临时状态 | 上传进度、当前分片、编辑草稿 | 根据恢复需求选择客户端或临时表 |
| 文档注释字段 | 示例说明、演示标记 | 不误存入正式证据表 |

不得简单执行“原型增加一个字段，数据库就增加一列”。

### 7.4 数据库迭代规则

- 通过版本化迁移脚本修改，不直接手工修改共享数据库；
- 优先新增兼容字段，避免无计划删除或重命名；
- 修改字段含义时，必须同时检查历史数据、API 和导出；
- 数据迁移应具备回滚或补偿方案；
- 首版字段不完整可以作为技术债记录，但核心身份、租户、权限和审计字段不得缺失。

## 八、API 契约与联调规则

1. 后端主导 OpenAPI，前端在开发前确认页面可用性；
2. 请求、响应、错误码、分页、权限和幂等规则必须明确；
3. 前端可以先按契约使用 Mock，不必等待全部后端完成；
4. 联调以首条业务链为单位，不在所有页面完成后一次性对接；
5. 兼容新增可选字段可以进入当前版本；
6. 删除字段、修改类型或改变业务含义属于破坏性变更，必须评估调用方并决定是否升级版本；
7. 前端不得绕过 API 自行实现审批、完整度或权限核心规则；
8. 后端不得只返回字段而不实现对应业务约束；
9. API 与原型不一致时，先判断是展示调整还是业务规则变化，再决定修改哪一端。

## 九、测试协同规则

每个开发切片均应同步提供：

- 正常流程用例；
- 非法状态转换用例；
- 权限拒绝和跨租户用例；
- 空数据、重复提交和并发操作用例；
- 网络失败、服务失败和补偿用例；
- 数据库与 OSS 一致性检查；
- 必要的原始日志和测试证据。

缺陷等级建议：

| 等级 | 示例 | 处理原则 |
| :--- | :--- | :--- |
| P0 | 跨租户泄露、法定流程错误、原始证据可篡改、数据丢失 | 立即停止相关交付并修复 |
| P1 | 核心业务无法闭环、权限错误、状态错误、严重兼容问题 | 当前切片验收前修复 |
| P2 | 局部交互、展示、一般文档和可维护性问题 | 纳入迭代，不无期限阻塞开发 |
| P3 | 体验和优化建议 | 进入产品 backlog |

---

## 十、专家评审协同规则

专家评审按以下方式开展：

1. **启动评审**：确认重大方向和明显错误，不追求全部技术细节；
2. **专题评审**：只针对多租户、证据链、法定流程等高风险问题；
3. **切片评审**：首条业务链联调后，根据真实产品复核；
4. **准入评审**：试点或全量上线前检查校审、PoC、测试和合规证据。

评审意见必须标明：

- 是否阻塞当前开发切片；
- 是否只阻塞试点或全量上线；
- 责任团队；
- 可验证的完成条件。

一般文字、样式和可维护性建议不得默认设置为整个项目的开发阻断项。

## 十一、GitHub 协作规则

### 11.1 分支建议

- `feat/<scope>`：新功能；
- `fix/<scope>`：缺陷修复；
- `docs/<scope>`：文档与规则；
- `test/<scope>`：测试和 PoC；
- `chore/<scope>`：工程和依赖维护。

### 11.2 Pull Request 要求

每个 PR 应尽量聚焦一个主题，并包含：

- 目的和范围；
- 关联 Issue 或决策记录；
- 修改的 PRD、原型、数据库、API 或测试；
- 已执行的生成、迁移、测试和校验命令；
- 对前端、后端、数据库和测试的影响；
- 未解决事项和后续计划。

### 11.3 评审人建议

| 变更类型 | 必须参与评审的人员 |
| :--- | :--- |
| PRD、角色、业务流程 | 产品负责人，必要时业务专家 |
| 架构、数据库、API | 技术负责人及相关开发人员 |
| 原型与前端交互 | 产品负责人和前端负责人 |
| 测试、权限、证据链 | 测试负责人，必要时专家 |
| 试点或上线准入 | 四方共同评审 |

### 11.4 版本与变更记录

- PRD、架构、数据模型和 API 应保留版本历史；
- 已冻结版本不得直接覆盖修改，应通过变更记录产生新版本；
- 代码、迁移和文档尽量在同一 PR 中同步；
- 禁止通过强制推送覆盖共享历史；
- 禁止在未确认的情况下删除他人未提交工作或评审材料。

## 十二、开发与上线门禁分离

不得将“允许开发”和“允许正式上线”混为一谈。

| 门禁 | 必须满足的条件 | 未满足时允许做什么 |
| :--- | :--- | :--- |
| 基线与原型开发 | 技术选型、核心角色和首条业务链明确 | 当前已可开展 |
| 首条链联调 | 核心数据模型、OpenAPI、原型和基本测试可用 | 可继续其他公共能力开发 |
| 业务试点 | 目标节点校审、行为测试、PoC、法务及隐私复核通过 | 可继续开发和内部测试 |
| 全量推广 | 全量范围校审、完整测试、运维和合规证据通过 | 不得宣称全量就绪 |

当前仓库中的 `business_readiness=BLOCKED` 表示不得直接全量上线或推广，不表示禁止技术基线、原型和限定范围开发。

## 十四、规则修订

本规则需要修订时，应通过 GitHub PR 提交，并至少由产品负责人和技术负责人共同评审。涉及测试流程或专家评审职责的修改，应同时征求对应团队意见。

本规则自合并至 `main` 分支起执行。各团队已有工作不必推倒重来，但后续新增任务、交接和变更应按本规则留痕和协同。
