## 一、三个身份概念（PRD 术语基础）

| 概念 | 回答的问题 | 说明 |
| :--- | :--- | :--- |
| **登录账号** | 这个人能不能登录 | 账号本身不代表任何企业或项目权限 |
| **租户成员（界面用"企业成员"）** | 这个人属于哪家企业、能做什么管理 | 界面不用"会员" |
| **项目成员** | 这个人在哪个项目当总监/专监/监理员、负责哪些危大类别 | **企业身份和项目身份是两回事** |

## 二、角色与正式名称（7 角色，PRD/界面统一使用）

| 范围 | 正式名称 | 要点 |
| :--- | :--- | :--- |
| 平台 | 平台超级管理员 | 平台最高管理；可按规定兜底处置企业拥有者移交 |
| 平台 | 平台系统管理员 | 租户开通、平台配置等日常 |
| 企业 | **企业拥有者** | 每家企业**恰好一人**；企业内唯一超管；只能通过专门"移交"变更 |
| 企业 | **企业管理员** | 可零可多；由企业拥有者授权，各人权限可不同 |
| 项目 | 总监 | 按项目任命 |
| 项目 | 专业监理工程师（专监） | 按项目任命并指定负责的危大类别 |
| 项目 | 监理员 | 按项目任命，处理本人任务与现场采集 |

命名注意："企业拥有者"是系统所有权身份，不代表股权/法定代表人；租户侧统一叫"企业管理员"（勿与平台"系统管理员"混淆）；"租户超管"只是企业拥有者的解释用语，**不设第二个角色**。

## 三、企业拥有者 vs 企业管理员（PRD 必须表达的核心差异）

| 操作 | 企业拥有者 | 企业管理员 |
| :--- | :---: | :---: |
| 新增/停用企业成员 | 默认可以 | 获相应权限后可以 |
| 设置管理员、分配管理权限 | 默认可以 | 获权限后可以，**不能越权授权** |
| 创建项目 / 任命项目角色 | 默认可以 | 获相应权限后可以 |
| **移交企业拥有者** | 可以（本企业内） | **永远不可以** |
| **停用/删除/降权企业拥有者** | —（走移交） | **永远不可以** |
| 以企业身份直接做项目法定签署 | 不可以（仍需项目任命） | 不可以（仍需项目任命） |

**红线：权限全给也不等于拥有者。** 页面与权限说明必须写明这一点。

## 四、项目角色必须按项目任命

- 总监/专监/监理员**不是企业级角色**；同一个人可以在项目 A 当专监（负责基坑+起重）、项目 B 当总监、项目 C 无任何角色。
- 任命规则：① 只有具备项目任命权限的企业拥有者/管理员可任命；② 对象必须是本企业有效成员；③ 专监必须指定该项目负责的危大类别；④ 总监负责该项目全部危大类别；⑤ 监理员以本人任务为主；⑥ 角色变更不改写历史记录中的当时身份。

## 五、PRD 第一段必须覆盖的核心流程

1. **平台开通企业**：填企业信息→创建/绑定首名成员→自动设为企业拥有者→全流程成功才算开通（**不能出现"已开通但没有拥有者"**）。设计：开通表单、首名成员信息、成功/失败反馈、开通记录。
2. **企业新增成员＋设管理员**：有权限者新增/绑定成员→设为企业管理员→在允许范围内勾选权限→未授权成员不显示管理入口。
3. **创建项目并任命**：创建项目→从本企业有效成员中任命总监/专监/监理员→专监配置危大类别→成员只见权限范围内的功能与数据。
4. **移交企业拥有者**（两条路径）：企业内（当前拥有者发起）/平台兜底（专门权限平台管理员发起，必填原因，用于拥有者离职/停用/失联）。确认页必须展示：当前拥有者与接收人、接收即生效、原拥有者立即失去身份与超管权限、**双方项目任命与历史记录不变**、原拥有者保留成员身份（如需管理员权限由新拥有者另授）、需二次确认、双方可能需重新登录。**一期为确认后直接生效，不做"等待接收"流程。**

## 六、异常与提示场景（PRD/原型至少覆盖）

1. 管理员未获某项管理权限时的入口展示与拦截；
2. 管理员尝试移交拥有者、停用拥有者、越权授权时的拒绝提示；
3. 选择已停用成员/其他企业成员作为拥有者接收人时的拦截；
4. 原拥有者移交后继续用旧会话的失效反馈；
5. 企业被冻结、账号被停用、成员被停用后的登录/访问反馈；
6. 未被任命到项目的人访问项目功能；专监访问未分配危大类别；
7. 拥有者/管理员未任命总监却尝试总监签署时的拒绝；
8. 平台无专门权限的管理员尝试兜底移交的拒绝；
9. **跨企业流转（历史可多企业、在职仅单企业）**：同一登录账号任一时刻只能属于 **1 家有效（启用中）企业**，不允许同时在多家企业履职，**不做企业切换交互**；从原企业退出时由原企业停用成员（保留历史记录不删除），新企业可直接绑定该原账号入职，无需重新注册。若账号在其他企业仍为启用状态，新企业绑定时服务端拦截并提示“该账号当前已在其他企业任职，须先由原企业停用成员关系后再加入”；若原企业已整体冻结导致无法自行停用，由平台管理员停用原企业成员关系以释放账号。

> 所有拦截以**服务端结果**为准，前端隐藏按钮仅为体验优化。

## 七、产品可细化 / 不得改变

**可细化**：页面布局、字段展示、表单校验、提示文案、邀请/绑定交互、权限分组展示、任命操作流程、审计查询展示。

**不得改变**（如业务确需变更，须作为重大架构变更重新提交技术评审）：
1. 每家企业只有一名企业拥有者；
2. 拥有者与管理员的身份差异（管理员不能经授权获得所有权专属能力）；
3. 总监/专监/监理员按项目任命；
4. 企业角色不自动产生项目法定签署权；
5. 平台执行移交不等于平台成为企业拥有者。

## 八、PRD 交付清单（第一段）

1. 角色与术语章节（用第二节统一名称，分平台/企业/项目三个范围）；
2. 角色权限矩阵（企业管理权限与项目业务权限**分列**，不混一张无范围区分的表）；
3. 平台端页面：企业开通（含首名拥有者）、平台兜底移交、移交审计记录；
4. 租户端页面：成员管理、管理员设置与权限分配、拥有者移交、项目管理、项目成员任命、专监危大类别配置；
5. 移动端规则：当前项目、当前项目角色、专监危大范围与权限不足表现；
6. 流程与状态：开通/成员新增停用/权限授予回收/项目任命变更/所有权移交；
7. 异常与提示文案（覆盖第六节全部场景）；
8. 验收用例至少覆盖：唯一拥有者、管理员不能替代拥有者、项目角色跨项目独立、专监危大范围、移交后权限即时生效、历史归属不变、跨企业流转（在职单企业拦截＋原企业停用后复用原账号加入新企业）。

## 九、与后续内容的关系（勿混入第一段）

- **节点库管理页（平台维护基线＋租户扩展、手标 V/P）**：属第二段，等新契约拍板后交接——PRD 第一段可预留"标准节点库"入口占位，不展开。
- **采集/审核/归档/出证/隐患闭环**：第二段，依据后续契约与 B6 生成物"引用＋受控嵌入"，禁止手改契约。
- 角色权限矩阵中节点/采集相关权限列，第一段可留空占位并注明"待第二段契约"。

> 一句话交接口径：**平台管角色规则和租户开通，企业拥有者唯一且只能移交，企业管理员按授权协助管理，总监/专监/监理员按项目任命；企业身份不等于项目签署权。第一段照本文件写，第二段等通知。**
