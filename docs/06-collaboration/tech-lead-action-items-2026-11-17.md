## 任务 A：FastapiAdmin 解耦异议的架构裁决（ADR）—— **需要技术负责人拍板**

**争议**：产品团队要求"解除对 FastapiAdmin 的深度依赖，改用原生 FastAPI + SQLAlchemy 2.0 + Pydantic v2 重写"（理由：小众项目供应链风险、未来信创/政企适配）。

**评审方评估**（详见第二轮回应第二节）：

- FastapiAdmin 本身就是 FastAPI + SQLAlchemy 2.0 + Pydantic v2 的应用脚手架，并非替代性技术路线；
- 信创适配（达梦/金仓方言、国密算法、国产 OS）与框架选型基本正交；
- 基线已导入 1,182 文件并通过真实运行验收，推翻重写为负收益。

**评审方建议结论：维持现有选型**，以以下工程约束回应风险关切：

| 约束 | 内容 |
| :--- | :--- |
| 供应链自持 | 锁完整 commit + `vendor/` 本地留存 + 关键能力自研增强，不依赖上游持续维护 |
| 代码侵入隔离 | 业务代码集中 `src/` 应用层；基线修改以补丁/扩展登记，禁止大面积改写 vendor 原生代码 |
| 数据库方言抽象 | 数据访问层禁用方言专属特性清单化，为达梦/金仓预留方言层（技术债登记，非一期任务） |
| 国密/信创登记 | 登记为未来扩展项，在网关/传输层评估，不作为当前重写理由 |

**请回应**：同意 / 修改约束 / 推翻选型（如推翻请附成本评估）。裁决后以 ADR 形式留痕于 `docs/03-architecture/`。

## 任务 B：研究报告正文风险定性回填 —— **双方无争议，可立即执行**

**背景**：已实证确认《研究报告初稿》正文第 4 章有 135 处 ★、38 处 △ 逐节点定性 + 4 处"全部节点"批量声明 + 类级声明，而 `scripts/generate_baseline_data.py` 仅读取附录 A 表格导致 331 条误标 `PENDING_REVIEW`。产品团队与评审方对"需要回填"无争议，**无需等待任何裁决**。

**执行要求**：

1. 扩展生成脚本解析正文第 4 章（4.2~4.12 节）节点段落定性与批量声明，建立"正文段落 → 附录表格行"映射；
2. 产出**三份清单**（不强行凑 100% 覆盖）：
   - 自动 CONFIRMED 清单（每条附"研究报告 4.X 节"确认依据）；
   - 映射歧义行清单（正文粒度粗于附录行的边界项，交产品团队组织业务专家快审）；
   - 正文与表格内容冲突行清单（如 A-2 已知错配）单独登记；
3. `source_review_status` 按实际映射结果更新；CONFIRMED 节点按既有规则进入任务分母。**BLOCKED 其余维度（PoC/合规/行为）不因回填改动**，冻结边界不变。

**分工说明**：脚本属工程实现，正常由技术团队执行。评审方已提出可起草"脚本草案 + 映射验证报告"以 PR 形式提交、技术团队审查合并（方案 A），或仅提供映射规则由技术团队自写（方案 B）——由项目负责人指派后动工。
