## 一、为什么需要这份说明

PRD 在约一个月内经历了 5 个版本（v1.0 → v2.0 → v2.1 → v2.2 → v2.3 → v2.4）。修改的直接原因有两个：

1. **技术负责团队在架构选型与基线搭建过程中发现 PRD 存在会影响技术实现的问题**（数据口径矛盾、技术能力超承诺、字段契约不唯一等）；
2. **第三方专家评审对每个版本进行复审**，复审发现的问题驱动了下一轮修改。

由于产品团队尚未纳入仓库版本控制，看不到每一轮修改的上下文，本说明按时间线还原每一版"遇到了什么问题、为什么改、改了什么、复审结论是什么"，便于产品团队判断：**哪些修改必须接受（客观纠错），哪些修改属于业务决策，产品团队有权提出异议。**

## 三、各版本详细说明

### 3.1 v1.0 正式版（2026-10-19）：初始版本

原始 PRD 奠定了业务主线：企业入驻 → 项目配置 → 清单驱动采集 → 审核闭环 → 证据链归档出证。这个主线在后续所有版本中**没有改变**。

首次第三方评审（2026-11-12，`docs/01-review-reports/document-feasibility-review-2026-11-12.md`）发现的主要问题：

**数据口径类（客观错误）**

- 节点总数算术错误：正文各分项相加为 362，汇总却写 342；且 342 的来源是课题研究清单，不是住建部法定节点库，不能宣称"住建部 342 个标准工序"；
- 字段数量错误：附录 B 原始字段实际 24 项（11+6+3+4），PRD 写 26 项；
- 同一字段多处口径冲突：B010 一处 20 字、一处 50 字；B007 时间精度一处秒级、一处毫秒级；
- 原始清单子类别内序号重新从 1 编号，PRD 直接当全局唯一编码使用。

**技术原理类（会影响实现正确性）**

- 把文件自身 SHA-256 写入该文件水印——写入后文件已变，哈希自指循环，不能自我证明；
- ETag/CRC64/抽样哈希不能等同全文件 SHA-256 完整性核验；
- 离线配额 50 张照片 + 5 段视频最高约 550MB，超过微信官方本地存储 200MB 上限；
- 宣称提取完整 EXIF 相机参数、自动识别 Fake GPS——微信官方接口无此承诺。

**权限与业务闭环类**

- 超级管理员"放行全量跨租户"与租户隔离目标矛盾，且保留超管使用小程序全部页面、代行审批的旧规则；
- 严重隐患"停工、报告建设单位、拒不整改时报告主管部门、复工审查"的法定流程缺失，仅有 48 小时催办；
- 验收双签、验收合格后方可进入下一道工序的门禁未落成系统规则；
- 一期不设施工单位角色，却写"施工单位提报整改后照片"，责任主体断链。

**框架选型报告事实错误**

- 所引用开源框架的提交日期、tag 版本与官方仓库不符；
- `FastapiAdmin` 用户状态实际为 0=启用、1=停用，架构文档若按 status==1 判断正常，会把认证逻辑写反。

### 3.2 v2.0 架构对齐版（2026-11-12）：需求与架构对齐

**修改原因**：技术架构选型敲定（FastapiAdmin 主骨架 + RuoYi-FastAPI 能力借鉴，平台端/租户端/小程序三前端分离），原 PRD 未反映这些架构决策。

**主要修改**：

- 引入平台域与租户域两级解耦的角色体系；
- 明确"一后端三前端"终端矩阵；
- 面向 AI Agent 开发模式重写数据契约章节。

**评审结论**：方向正确（平台/租户分离、项目级角色被评为"值得保留的设计决策"），但首次评审指出的数据口径、技术原理、权限矛盾等问题在本版中**大多仍未解决**。

### 3.3 v2.1 评审闭环版（2026-11-13）：第一轮集中整改

**修改原因**：产品负责人针对首次评审的 12 项问题（DOC-01~DOC-12）逐项核销，并首次引入机器可读基线（节点种子库 + 字段字典 JSON）。

**确实有效的修改**：

- GB/T 50319 表号部分纠偏（旁站记录改为 A.0.6）；
- 原始帧摘要与归档文件摘要分离（双哈希）；
- 离线配额从"50 张/5 段"改为 150MB 字节预算；
- 超管验收用例改为默认只读 + 二次授权。

**复审（2026-11-14，`prd-v2.1-follow-up-review-2026-11-14.md`）发现的问题**：

- **核销表与正文脱节**：文档头部核销表宣称"已修复"，但正文、ER 模型、页面规则、验收用例仍保留旧规则（超管全量放行、50 张/5 段配额等）；
- **节点种子库编码大量重复**：347 条记录只有 244 个不同编码，103 条重复（如 `A-04-01` 同时对应 6 种不同业务含义），而 ER 把 node_code 定义为唯一键，导入即冲突；
- **原始空白被擅自补值**：原始 A-8 清单中两项未标风险等级，种子库直接补成 △，不属于"忠实提取"；
- **字段字典与 PRD 仍不是同一契约**（B301 列名、B010/B104/B304 长度、B011 生成方、B003 阶段枚举等多处冲突）。

### 3.4 v2.2 评审整改中（2026-11-15）：结构性根治

**修改原因**：v2.1 复审证明"文本打补丁"方式无法消除矛盾，本版转向**单一事实源（SSOT）全量重生成**。

**主要修改**：

- **节点唯一身份模型重建**：`node_uid`（全局唯一）与 `legacy_node_code`（原始清单业务编号）分离，每条记录保留原始文档、表格、行号溯源；
- **原始数据忠实原则**：原始清单风险等级空白一律标 `UNSPECIFIED + PENDING_REVIEW`，不再擅自补值，待业务专家逐条确认；
- **口径修正**：采集基线明确为"11 类专业危大课题清单 + 1 个通用应急兜底模块（5 个场景）= 347 条基线记录"，不再宣称 342；
- **法定履职全闭环**：补齐严重隐患停工签发/送达/拒收、报告建设单位、拒不整改报告主管部门、复工申请审查、验收双签与下一道工序门禁的完整状态与用例；
- **任务发生实例（Occurrence）模型**：同一节点可按楼栋、部位、施工批次、日期重复发生，完整度分母按实际应采发生数计算；
- **生成脚本纳入仓库**，个人信息保护专节（第 7.7 节）。

**复审发现**：生成结果可复现、347 个 UID 唯一通过，但 PRD 示例节点引用错误（一个 UID 不存在、一个风险状态与种子库相反）、B004/B005/B006 字段语义划分不当、架构文档未同步、表号映射仍有三处错误（方案报审应为 B.0.1、暂停令应为 A.0.5、通知回复单应为 B.0.9）。

### 3.5 v2.3 评审整改中（2026-11-15）：GitHub 协作与快速迭代

**修改原因**：为避免文档频繁修改造成版本混乱，项目转入 GitHub 仓库协作；技术团队在此期间完成多轮小步修复：

- 表号映射全部修正（F04→B.0.1、暂停令→A.0.5、回复单→B.0.9）；
- 扩展列口径统一（25/28 漂移修正为实际值，最终 30 个）；
- 示例改为真实节点派生、演示哈希为合法 64 位并显式标记合成数据；
- 旧命名公式、`task_instance_id`、超管代管审批描述全部清理；
- 建立 CI 一致性校验（37 → 53 → 91 → 93 → 94 项逐步强化）；
- 新增业务校审清单与技术 PoC 验证清单两份工作模板；
- **修复两项执行阻断**：人工校审结果持久化（`source_review_decisions.json`，重跑不覆盖专家结论）；综合业务准入门控（六维状态聚合，禁止"待审归零即自动 READY"）。

### 3.6 v2.4 基线冻结版（2026-11-16）：当前需求基线

**冻结决策**：v2.3 通过全部静态校验（94/94）并完成执行阻断修复后，技术负责团队确认**不再存在影响技术基线搭建的需求偏移**，决定冻结。

**冻结边界**（重要）：

- `business_readiness = BLOCKED` 保留，但含义仅限于：**业务试点上线与全量推广**须待源数据校审（331 条待审节点）、真机 PoC、法务合规复核、行为验收完成；
- **技术基线搭建、前端原型开发、限定范围业务链开发不受任何阻塞**；
- 冻结后任何需求修改走受控变更：GitHub Issue/PR + 决策记录，由生成脚本重新产出文档，**禁止手工直接编辑**。

## 四、贯穿五轮修改的三个根本转变

理解这三点，就能理解为什么修改如此频繁：

1. **从"手写文档"到"单一事实源"**：v1.0~v2.1 的矛盾大多源于同一规则在文档多处手写、改一处漏一处。v2.2 起节点库、字段字典、示例、验收用例全部由脚本从原始材料生成，CI 校验一致性，这类矛盾从根源消除。
2. **从"结构通过"到"业务准入分离"**：早期"校验通过"容易被误读为"可以开发上线"。现在结构校验、源数据校审、技术 PoC、合规复核、行为验收是五个独立状态，`BLOCKED` 只约束上线，不约束开发。
3. **从"技术承诺"到"能力边界诚实"**：EXIF 范围、Fake GPS 识别、离线容量、哈希与司法效力等表述，全部改为与微信官方能力、对象存储实际能力、司法实践一致的克制口径。

## 五、请产品团队重点确认的业务决策类修改

以下修改**不是纯技术纠错，而是改变了产品语义**。产品团队如认为与用户需求不符，请按第六节渠道提出异议：

| # | 修改内容 | 原口径 | 现口径（v2.4） | 影响 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 采集基线定位 | "住建部 12 大类 342 个标准工序" | "11 类专业危大课题清单 + 1 个通用应急兜底模块，共 347 条基线记录"；347 条中 331 条风险等级待业务专家确认 | 节点库是课题研究成果而非法定标准；**待确认节点不进入正式强制采集任务和完整度分母**，原型可先按全量展示 |
| 2 | 应急模块 | 独立第 12 大类、26 节点、按三阶段划分 | 通用兜底模块、5 个场景、不分阶段（依据研究报告 4.13 节） | 原型中应急模块的页面结构需对应调整 |
| 3 | 超级管理员能力 | 全量跨租户放行、小程序全功能、可代行审批 | 平台端受控代管穿透、默认只读、导出/督办需二次授权、**不得代替法定责任人签字** | 影响平台端原型中"代管"相关交互设计 |
| 4 | 施工单位角色 | "施工单位提报整改后照片"触发超期 | 一期不设施工方账号；施工方线下提交盖章回复单，由监理登记原件来源，监理员拍摄复查照片 | 整改闭环页面的填报主体和字段需按此设计 |
| 5 | 离线配额 | 50 张照片 + 5 段视频（最高约 550MB） | 150MB 字节预算（约 25~30 张照片 + 1~2 段短视频），按剩余字节而非张数控制 | 影响小程序离线拍摄交互与提示文案 |
| 6 | B011 媒体编码生成方 | 服务端生成 | 端侧离线生成、服务端校验 | 支持离线场景的必然选择 |
| 7 | B302 时间戳语义 | "平台上链存证时间戳" | 服务端固化接收时间（一期不上链） | 证据详情页的时间字段含义 |
| 8 | 保管期限 | 笼统"云永久" | ★云+异地永久、△按期清理、到期销毁须审批并保留清单哈希；原始取证文件严禁任何角色物理删除 | 归档/清理相关页面与规则 |

纯技术纠错类修改（表号 B.0.1/A.0.5/B.0.9、双哈希分离、命名公式、字段长度统一等）不影响产品语义，无需异议流程，但原型涉及表单编号处请以 v2.4 为准。

## 六、异议与变更渠道

1. **对业务决策类修改有异议**：请在 GitHub 仓库提 Issue（标注 `PRD-v2.4-baseline`），或直接反馈给技术负责人转交；异议期内（建议自收到本说明起 5 个工作日）相关条目视为待复核；
2. **原型开发中发现 PRD 与真实业务冲突**：按 `docs/06-collaboration/team-collaboration-and-delivery-workflow.md` 的受控变更流程提交，不要自行按旧版本或个人理解实现；
3. **任何修改都不再直接改文档**：所有变更经确认后由生成脚本重新产出 PRD，保证版本间可追溯。
