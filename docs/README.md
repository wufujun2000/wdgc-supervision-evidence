# 项目文档中心

本文件是危大工程监理履职证据链系统的文档总目录，记录各目录和文件的用途、当前有效版本、生成关系及阅读顺序。

项目总体介绍和工程入口见根目录 [`README.md`](../README.md)。开发 Agent 应先阅读根 README，再通过本文件定位具体依据，不应直接从历史版本或历次评审意见推断当前需求。

## 一、当前文档基线

| 维度 | 当前状态 | 查阅位置 |
| :--- | :--- | :--- |
| 当前需求版本 | PRD v2.4 基线冻结版（2026-11-16 冻结），技术基线搭建与前端原型开发的当前需求基线 | `02-prd/PRD_v2.4_基线冻结版.md` |
| 当前架构版本 | 总体架构 v1.5 基线冻结版，技术基线已确定并开始搭建 | `03-architecture/system-architecture-design.md` |
| 节点结构 | 347 条基线记录、347 个唯一 `node_uid` | `04-baseline-data/hazard_nodes_seed.json` |
| 标准字段 | 24 个标准编号字段、30 个内部扩展列 | `04-baseline-data/metadata_and_forms_dictionary.json` |
| 校审人工输入 | 独立保存专家决定，生成器按节点与源指纹合并，重跑不覆盖 | `04-baseline-data/source_review_decisions.json` |

| 业务上线准入 | BLOCKED，不表示禁止技术基线、原型和限定范围开发 | `04-baseline-data/validation_report.json` |

当前文档、数据和评审材料较多，是因为项目处于需求定版、原型开发与技术基线并行阶段。随着真实代码、数据库迁移、OpenAPI 和测试报告形成，后续开发应逐步以工程产物和实测结果为直接依据。

## 三、PRD 产品需求文档：`02-prd/`

| 文件 | 用途与当前定位 |
| :--- | :--- |
| `PRD_v2.4_基线冻结版.md` | **当前需求阅读版本**。v2.3 通过全部静态校验与执行阻断修复后冻结升版而来，是技术基线搭建与前端原型开发的当前需求基线。包含角色、功能、任务发生实例、证据链、数据规则、页面和验收要求。由 `scripts/generate_prd.py` 生成，不直接手工修改 |
| `PRD_版本演进说明_v1.0至v2.4.md` | **产品团队交接用版本演进说明**。还原 v1.0→v2.4 每版的问题、修改原因与复审结论，并列出需要产品团队确认的业务决策类修改与异议渠道 |
| `PRD_v2.2_评审整改中.md` | 历史版本。引入节点唯一身份、原始数据溯源和业务准入状态，供追踪整改过程。v2.3 已冻结升版为 v2.4，其快照可从 Git 提交记录追溯 |
| `PRD_v2.1_评审闭环版.md` | 历史版本。首次针对第三方审查进行集中整改，供差异对照 |
| `PRD_v2.0_架构对齐版.md` | 历史版本。用于产品需求与平台/租户/小程序架构对齐 |
| `PRD_v1.0_正式版.md` | 初始 PRD，作为原始需求和历史问题对照，不作为当前开发依据 |

阅读规则：新需求开发默认阅读 v2.4 基线冻结版；旧版本仅用于理解变更原因。发现 v2.4 与原型或真实业务冲突时，应通过受控变更（GitHub Issue/PR + 决策记录）和生成器修订，而不是从历史版本复制规则。历史 PRD 中可能保留原作者机器的 `file://` 本地链接，这些链接仅作历史留痕，不属于仓库可访问文件，Agent 不应据此判断仓库缺件。

## 十、生成与校验脚本：`../scripts/`

| 文件 | 用途 |
| :--- | :--- |
| `generate_baseline_data.py` | 从原始 Word/Excel 生成节点、字段字典、校审台账和准入报告 |
| `generate_prd.py` | 从基线和字典生成当前 PRD（v2.4 基线冻结版）到 `docs/02-prd/` |
| `validate_prd_consistency.py` | 校验 PRD、架构、节点、示例、命名和关键规则一致性 |

统一执行方式：

```bash
python3 scripts/generate_baseline_data.py
python3 scripts/generate_prd.py
python3 scripts/validate_prd_consistency.py
```

执行后必须检查生成结果和 Git 差异。校验具体数量以 `04-baseline-data/prd_consistency_report.json` 为准，不在多个文档中手工维护固定数字。

## 十一、不同角色的阅读路线

### 产品负责人

1. 当前 PRD v2.4 基线冻结版；
2. 协作与交付规则；
3. 原始履约表及研究报告；
4. 业务校审清单；
5. 与当前变更相关的评审报告。

### 技术负责人及后端开发

1. 当前 PRD v2.4 基线冻结版；
2. 总体架构和框架选型；
3. 机器可读字段与节点基线；
4. 协作规则中的数据模型、API 和迁移要求；
5. 技术 PoC 清单。

数据库字段和 API 由技术团队主导设计；遇到业务含义不明确时，向产品和业务专家提出具体问题，不直接猜测。

### 前端及移动端开发

1. 当前 PRD 的角色、功能和页面章节；
2. 协作规则中的原型交接和 API 联调要求；
3. 原型工程及 Mock 数据；
4. 当前 OpenAPI 或接口契约形成后，以契约为联调依据；
5. 技术 PoC 中与相机、离线和上传相关的部分。

### 测试团队

1. 当前 PRD 验收章节；
2. 协作规则中的测试协同和缺陷分级；
3. 技术 PoC 清单；
4. 数据模型、API 和真实页面形成后的行为契约；
5. 历史评审中涉及权限、证据链和法定流程的风险项。

### 专家评审团队

1. 当前 PRD 与架构，而非旧版本；
2. 原始材料与最新基线；
3. 当前真实代码、测试和 PoC 证据；
4. 本目录中的历史报告，仅用于避免重复提出已解决问题。

## 十二、文档维护规则

1. 新增文档必须放入对应目录，并在本 README 中登记用途；
2. 当前有效版本与历史版本必须明确区分；
3. 生成文件不直接手改，应修改原始输入或生成器；
4. 移动文件时必须同步修正脚本、README 和跨文档链接；
5. 临时沟通材料不属于正式基线，需要长期保留时应整理为正式文档后归档；
6. 评审报告保留历史判断，不回写为当前需求；
7. 后续形成数据库、OpenAPI、真实前后端工程和测试报告后，应在根 README 与本文件中增加对应入口；
8. 所有变更通过 GitHub 留痕，具体协作方式见 `06-collaboration/team-collaboration-and-delivery-workflow.md`。
